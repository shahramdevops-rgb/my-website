هر کارت یک تصمیم از یک پروژهٔ واقعی است: مسئله‌ای که با آن روبه‌رو بودم، چیزی که انتخاب کردم و دلیلش — همراه با
بهایی که داشت. سه کارت اول مال همین سایت‌اند، پس همین‌جا می‌توانید نتیجه‌شان را ببینید.

<DecisionList>
    <Decision project="همین سایت" title="یک مبدأ برای فرانت‌اند Next.js و API با ASP.NET Core">
        <Challenge>
            این سایت باید React و دات‌نت واقعی را در کدی آمادهٔ production نشان دهد، و ورود ادمین
            باید با یک کوکی امن بماند — بدون قواعد CORS و بدون توکنی که JavaScript بتواند بخواندش.
        </Challenge>
        <Choice>
            دو اپلیکیشن پشت یک دامنه: Caddy درخواست‌های API را به ASP.NET Core می‌فرستد و بقیه را
            به فرانت‌اند Next.js.
        </Choice>
        <Why>
            برای مرورگر همه‌چیز یک سایت است، پس کوکی ورود بی‌دردسر کار می‌کند و هیچ اسکریپتی به
            توکن دسترسی ندارد. بهایی که پذیرفتم: به‌جای یک runtime، دو runtime که باید ساخته، منتشر
            و پایش شوند.
        </Why>
    </Decision>
    <Decision project="همین سایت" title="قرارداد تایپ‌شده بین فرانت‌اند و API">
        <Challenge>
            دو اپلیکیشن به دو زبان کم‌کم از هم دور می‌شوند: فیلدی را در بک‌اند تغییر نام بدهی و یک
            صفحهٔ React می‌شکند — در production، جلوی چشم بازدیدکننده.
        </Challenge>
        <Choice>
            API در هر build سند OpenAPI خودش را می‌نویسد. فرانت‌اند تایپ‌های TypeScript و کلاینت
            API را از همان سند می‌سازد، و اگر هر کدام قدیمی باشد CI شکست می‌خورد.
        </Choice>
        <Why>
            حالا تغییر قرارداد build را می‌شکند، جایی که خودم می‌بینم، نه صفحه را، جایی که
            بازدیدکننده می‌بیند. و دیگر هیچ تایپ دست‌نویسی نمانده که باید همگامش نگه داشت.
        </Why>
    </Decision>
    <Decision project="همین سایت" title="بدون Generic Repository روی EF Core">
        <Challenge>
            بسیاری از قالب‌های دات‌نت، Entity Framework Core را در یک Generic Repository و یک Unit
            of Work می‌پیچند: یک لایهٔ دیگر جلوی هر کوئری.
        </Challenge>
        <Choice>
            لایهٔ Application مستقیم با DbContext کار می‌کند، از طریق یک اینترفیس کوچک. خواندن‌ها
            projection بدون tracking هستند و فقط ستون‌هایی را می‌گیرند که صفحه لازم دارد.
        </Choice>
        <Why>
            DbContext در EF Core خودش همان Repository و Unit of Work است. یک wrapper عمومی یا
            قدرت کوئری‌ای را که لازم دارم پنهان می‌کند یا دوباره بیرون می‌دهد — در هر دو حالت،
            کدی واسطه که کاری جز پاس دادن ندارد. بهایی که پذیرفتم: لایهٔ Application به EF Core
            وابسته است.
        </Why>
    </Decision>
    <Decision project="سیستم مدیریت باشگاه" title="مونولیت ماژولار برای MVP">
        <Challenge>
            یک MVP که قابلیت‌هایش — عضویت، ورود و خروج، کمدها — هنوز در حال تغییر بودند، و تیمی
            کوچک که باید هم می‌ساختش و هم اجرایش می‌کرد. [placeholder] ماژول‌ها و اندازهٔ تیم را
            تأیید کنید.
        </Challenge>
        <Choice>
            یک اپلیکیشن و یک دیتابیس، که در داخل به ماژول‌هایی با مرزهای روشن تقسیم شده: هر ماژول
            جدول‌های خودش را دارد و به بقیه فقط یک اینترفیس عمومیِ کوچک نشان می‌دهد.
        </Choice>
        <Why>
            یک deploy و تراکنش‌های سادهٔ دیتابیس، تا وقتی دامنه هنوز در حال شناخته‌شدن بود — بدون
            فراخوانی شبکه‌ای و خرابی توزیع‌شده بین بخش‌هایی که با هم تغییر می‌کنند. مرزها راه جدا
            کردن سرویس‌ها را برای آینده باز نگه می‌دارند، اگر بار روزی آن را بخواهد.
        </Why>
    </Decision>
    <Decision project="سیستم رزرو سینما" title="دیتابیس تصمیم می‌گیرد صندلی مال کیست">
        <Challenge>
            دو نفر در یک ثانیه یک صندلی را انتخاب می‌کنند. هر دو آن را خالی می‌بینند؛ فقط یکی‌شان
            می‌تواند بگیردش — و دیگری باید همان لحظه بفهمد، نه دمِ درِ سالن.
        </Challenge>
        <Choice>
            گرفتن صندلی یک تغییر اتمیک در دیتابیس است، داخل یک تراکنش: فقط وقتی موفق می‌شود که
            صندلی هنوز خالی باشد. درخواست دوم صندلی را گرفته‌شده می‌بیند و پاسخ روشنی می‌گیرد که
            صندلی دیگری انتخاب کند. [placeholder] سازوکاری را که پروژه به کار برد تأیید کنید — قفل
            سطر (row lock)، ستون نسخه (version) یا قید یکتا (unique constraint).
        </Choice>
        <Why>
            بررسی در کد اپلیکیشن («خالی است؟ پس ذخیره‌اش کن») بین دو قدمش فاصله می‌گذارد، و با
            بیش از یک سرور حتی درخواست‌های دیگر را نمی‌بیند. دیتابیس تنها جایی است که همهٔ
            درخواست‌ها از آن می‌گذرند، پس قاعده همان‌جا باید باشد.
        </Why>
    </Decision>
    <Decision project="پلتفرم میکروسرویس" title="PostgreSQL و MongoDB، هر کدام جای خودش">
        <Challenge>
            بخشی از داده‌های پلتفرم تراکنش و رابطه‌های سخت‌گیرانه لازم داشت؛ بخش دیگر از رکوردی
            به رکورد دیگر شکلش عوض می‌شد و یک‌جا خوانده می‌شد. [placeholder] سرویس‌ها و داده‌ای
            را که هر کدام نگه می‌داشت نام ببرید.
        </Challenge>
        <Choice>
            هر سرویس دیتابیس خودش را دارد: PostgreSQL برای سرویس‌هایی با دادهٔ تراکنشی و رابطه‌ای،
            و MongoDB برای سرویس‌هایی که رکوردهایشان سندهایی با شکل متغیرند.
        </Choice>
        <Why>
            دیتابیس جدا برای هر سرویس، سرویس‌ها را مستقل نگه می‌دارد — هیچ سرویسی جدول‌های سرویس
            دیگر را نمی‌خواند. و هر دیتابیس در نقطهٔ قوت خودش کار می‌کند: قیدها و join در
            PostgreSQL، سندهای منعطفی که یک‌جا خوانده می‌شوند در MongoDB. بهایش: دو دیتابیس که باید
            اجرا، بکاپ‌گیری و خوب شناخته شوند.
        </Why>
    </Decision>
</DecisionList>
